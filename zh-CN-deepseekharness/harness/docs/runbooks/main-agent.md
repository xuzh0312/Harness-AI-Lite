# 主 agent 执行与验收手册

本手册规定通用行为流程，不包含后台调度器或运行器原生配置。入口是 [AGENTS.md](../../AGENTS.md)；角色职责以[角色协议](../../agents/README.md)为准，模型配置仅以 [MODELS.md](../../agents/MODELS.md) 为准。

## 1. 入口确认与任务记录

阅读 Harness 入口、[路径表](../paths.md)及目标目录适用的规则。确认三个区域的实际位置、读写权限、任务授权、当前代码状态和已有改动。若未提供路径但能从当前工作区可靠定位，先查看实际情况；未使用的区域标为不适用，只在确实缺少影响工作的细节时提问。

分别确认工作目录、规则加载和访问权限。Harness 是管理依据；执行目录按任务选择。软件命令通常在 `project/code` 运行，项目管理文档任务通常在 `harness` 运行。不要因目录在同一个工作区打开就认定它们共用仓库或权限。在 DSH 中，`workspace-write` 下默认以会话工作区为可写根，仍受当前文件策略约束。跨区域文件操作用绝对路径；例如在 Windows 上运行 `pwsh` 时，通过命令工具的 `workdir` 明确工作目录。确有需要且已获授权时，才为工作区外的具体写入操作申请最小范围权限；无法申请或被拒绝时报告阻塞，不换工具绕过。

对需要分派或持续跟踪的任务，按[计划模板](../plans/TEMPLATE.md)在 `active` 建立一份任务记录。走直接修改路径的功能任务无需新建；走功能规划路径则由 `feature-plan` 创建。如果已有记录，续接前先核对实际文件和证据。纯问答与轻微措辞调整无需正式计划，但仍应给出适用的验证结果。只有主 agent 更新共享记录与状态。

## 2. 定义验收与选择角色

先记录目标、非目标、允许修改范围、预期行为及验证方法。按 `ARCHITECTURE.md` 核对文件归属：软件实现放在 `project/code`，测试与辅助代码放在 `test`，`harness` 只存管理材料。优先澄清待定的关键需求；不影响目标的实现细节选择最小方案，并记录理由。

新增或增强功能时，中立地让用户在功能规划与主 agent 直接修改之间选择。选直接修改时，依授权范围执行，不要求新建功能规格书或实现计划。选规划时，阅读 [feature-plan](../../.agents/skills/feature-plan/SKILL.md)。缺少项目介绍时向用户询问；已选定但未记录技术栈时向用户核实。技术栈未定且用户选择共同规划时，和用户一起按 [tech-stack-plan](../../.agents/skills/tech-stack-plan/SKILL.md) 执行。只更新项目介绍和技术栈架构，随后重读这两份文档。主 agent 每次只向用户提一个问题，同时起草规格书，核查需求覆盖并生成编号实现清单。规格书与计划共用功能编号、分别版本化，并一同提交用户确认。在用户确认整组文档前，只做调查、讨论和规划文档，暂停依赖该确认的实现。局部回答不代表确认整组文档。确认后，在原计划跟踪已获授权的执行；有实质变更时，回到 `feature-plan` 修订文档并重新确认组合。其他任务走各自适用的流程，无需新建功能计划。

| 任务条件 | 角色与顺序 |
| --- | --- |
| 纯问答、轻微措辞调整 | 主 agent 直接完成并检查 |
| 范围明确的小型代码修复 | implementer → 两个 reviewer 并行审查 → 主 agent 验收 |
| 用户选择直接修改功能 | 主 agent 修改 → 按变更类型做适用的独立审查和验证 → 主 agent 验收 |
| 用户选择功能规划 | 主 agent 访谈并维护规格书与计划，有界面时先梳理用户任务 → 用户成对确认文档 → 按需细化并交接界面设计 → 获实施授权后逐项分派、审查、验收 → 整体审查与主 agent 验收 |
| 非功能任务中的跨模块或重要接口决策 | 主 agent 分析决策、核对需求与授权 → implementer → 两个 reviewer 并行审查 → 主 agent 验收 |
| 交互式界面设计 | 阅读 [UIUX-design](../../.agents/skills/UIUX-design/README.md) → UIdesign 经主 agent 转达问题和答案，向用户确认代表性页面，再将设计、状态和待做检查交接给主 agent |
| 环境、脚本、CI、构建或打包 | implementer → 两个 reviewer 并行审查 → 主 agent 验收；重要设计决策先由主 agent 分析 |
| 影响后续决策的规则变更 | 主 agent 或 implementer 修改 → 两个 reviewer 并行审查场景 → 主 agent 验收 |
| 代码与基础设施混合任务 | 先完成前置依赖；写入范围不重叠时，独立的 implementer 实例可并行。集成后由两个 reviewer 并行审查 |

只为任务所需的工作创建子 agent。凡需独立审查，主 agent 分派两个独立实例：reviewer-spec 检查规格符合性，reviewer-quality 检查实现质量。两者遵循 `MODELS.md` 中统一的继承策略。没有功能规格书时，reviewer 以任务需求和现有契约为准。代码、基础设施及影响后续决策的规则变更，必须取得两个相互独立且独立于作者的 reviewer 实例的报告，才能验收。

上表混合任务的并行实施只适用于非功能任务。功能计划获确认且具备实施授权后，使用 [subagent-driven-execution](../../.agents/skills/subagent-driven-execution/SKILL.md)。每个新的 implementer 上下文只分派当前实现项；完成实现、自查、两个并行审查、必要的返工与验证以及主 agent 验收后，才能开始下一项。必要的只读调查可并行。全部实现项通过后，新建两个 reviewer 做一次整体审查。

## 3. 分派与整合

使用[交接模板](../../agents/TASK_TEMPLATE.md)，明确路径、基线、写入范围、依赖、验收要求和角色配置。每次创建前重读 `MODELS.md` 的继承与禁用策略。新建独立上下文时使用本地 DSH `subagent`，不用 `subagent_fork`。使用不设子 agent 路由或推理深度默认值的 Spawn 配置，并省略 `provider`、`model` 和 `reasoning_effort`，以继承主 agent 的有效设置。已知覆盖与继承冲突时，报告阻塞，不用替代配置分派。在交接提示中提供绝对工作目录和全部必要材料。执行命令时使用 shell 工具的 `workdir`。每个新的同级实例使用唯一名称，最长 32 个字符，以小写字母开头，仅含小写字母、数字和连字符。不同实例可命名为 `reviewer-spec-01`、`reviewer-spec-02`；角色及审查维度仍为 `reviewer-spec`。交接提示和 `workdir` 都不会改变沙箱权限。

分派示例（将完整交接填入 `prompt`；不传模型覆盖参数）：

```text
subagent({ name: "reviewer-spec-01", description: "审查规格符合性",
  prompt: "<包含绝对工作目录的完整只读审查交接>" })
```

保存返回的 agent 名称，验收前收齐完成报告。用 `list_agents` 定位原实例；实例可联系时，用 `send_message` 按返回的名称续接。`inactive` 不代表任务已经完成。原实例无法续接时，新建实例并交接已核实的结果及待办事项。

遵守运行器的并发限制。容量不足时，仍以独立上下文顺序运行两个 reviewer，并记录实际顺序；其他任务容量不足时也顺序执行。不得并行写同一文件，子 agent 不得嵌套创建 agent。执行者工作期间，主 agent 也不得编辑已分派给该执行者的文件。先确认关键设计决策，再启动依赖该决策的实现。

收到结果后，在报告完成前核对实际文件、改动范围、结果及证据。主 agent 汇总共享记录。设计与原型只能保存到分派指定的 `test` 位置。reviewer 对被审查材料保持只读。发现越界改动时，先查明来源，保留用户的已有内容。

对于已确认的功能计划，将简报、执行者标识、分派前基线、交付与审查摘要、返工轮次和下一步统一记录在原计划。只分派当前项、必要接口、前置结果及全局约束。原始 diff、开工前未提交内容快照及验证产物放在 `test`；`harness` 只存管理摘要和引用。审查覆盖完整任务 diff，包括未提交的改动。

## 4. 审查、返工与阻塞

向两个 reviewer 提供相同的目标、需求来源、验收标准、设计、审查版本、完整任务 diff、执行报告及证据；两者独立形成初步判断。未提交的工作应提供文件范围和工作树状态，不以不存在的提交 SHA 当作基线。两份报告返回前保持审查版本不变；若外部改动导致版本变化，更新材料后重新审查，不混用不同版本。

每个实例针对分派的维度给出“建议通过 / 需返工 / 证据不足”，注明实例、维度、轮次、覆盖版本和证据；主 agent 保留两份结论。只有两份报告均建议通过、覆盖同一最终版本且必要证据齐全时才能验收；缺少报告或任一报告未通过，均不得标记完成。按证据处理冲突，不投票，也不用一份结论抵消另一份；重复发现去重但保留双方来源。返工优先续接原执行者和原来的两个 reviewer；无法续接或角色配置已变更时，按最新配置新建实例并交接上下文。同一版本的证据仍然有效时，不机械重跑检查。

同时提供 [bug-detect 技能](../../.agents/skills/bug-detect/SKILL.md)与[项目错误知识库](../bugs.md)。reviewer 发现缺陷或复验修复时调用技能，返回检索和记录建议。主 agent 写入前重读最新知识库，按根因去重，串行分配编号或更新原条目。并行 reviewer 不直接写入。同类问题复发时重新打开原条目，保留已验证方案的适用范围；没有新信息时不更新。

修复时向 implementer 提供相关 BUG 条目；使用既有方案前核查是否适用。验证后由主 agent 补记实际方案和证据，只有满足关闭条件才标记为已解决。知识库不可写时，返回未保存的建议并记录具体阻塞；强制审查和验证仍须进行。任务记录只引用最终的 BUG ID，不复制完整条目。

逐项明确采纳修复或驳回，并说明依据；主 agent 记录裁定。如果必须修改验收标准，回到需求确认；不通过删除检查或降低标准掩盖失败。修复后执行者重跑受影响的检查，两个 reviewer 分别核验相关发现、新 diff 与最终版本。未受影响的审查维度可复用有效证据，但主 agent 验收前，每个 reviewer 都必须明确检查当前版本。验证边界遵循 [reviewer 协议](../../agents/reviewer/AGENT.md)。

同一问题连续两轮返工仍存在且没有新证据时，主 agent 重新分析根因、方案和分派，不机械重试；需要用户决策时只提出具体未决事项。这条规则不要求自动停止仍在取得进展的修复。

缺少必要权限、依赖、外部服务、关键需求或强制审查能力时，记录具体阻塞、已尝试行动、影响及恢复条件。继续与该条件无关且已获授权的工作；恢复后从记录的位置续接，并确认已有证据仍有效。

## 5. 最终验收与状态

| 状态 | 进入条件 |
| --- | --- |
| 待开始 | 已明确目标，尚未执行 |
| 待确认 | 功能规格书和计划已起草或修订，当前组合等待用户确认；不得启动依赖该确认的实现 |
| 进行中 | 确认入口后开始分析、设计或实现 |
| 审查中 | 交付已可检查，正在审查或核验证据 |
| 返工中 | 已分派须修复的问题 |
| 受阻 | 缺少外部条件或关键决策，已明确受阻部分的恢复条件 |
| 已完成 | 范围、适用检查、强制审查和最终验收均满足要求 |
| 已取消 | 用户取消任务；记录原因并归档，不表示已经实现 |

主 agent 按实际情况更新状态。走功能规划路径时，用户成对确认当前文档并授权实施后，才能开始实现。实质修订回到“待确认”。用户只批准规划时，等待实施授权；返工修复后回到“审查中”。解除阻塞后续接对应阶段，并遵守尚未满足的确认要求。只有主任务自身的验收条件全部满足，才能将其标为“已完成”。

完成前逐项确认：

- 最终 diff 符合任务范围并保留用户已有改动；新文件符合三个区域的边界；未请求打包就不生成安装包。
- 已核查 `docs/paths.md` 的路径表和当前实际目录树，包括本任务造成的结构变化；明确指出未核查的区域，不声称同步已完成。
- 每项必需验收均有证据或合理的不适用说明；必需检查失败、未运行或缺少关键证据时，不标为通过。
- 证据记录工作目录、检查方法、结果、覆盖版本或工作树范围；后续改动影响的结论已重新验证，不重跑证据仍有效的无关检查。
- 所有阻断验收的问题均已修复并验证，或有符合已确认需求的明确裁定；不能把未满足的需求裁定为通过。
- 每个强制审查范围都有两个独立实例的报告，分别覆盖规格符合性和实现质量，均对同一最终版本建议通过。因容量不足而顺序审查时，如实记录，不声称并行。
- 只做规划时，核对交付的规格书和计划的版本、确认状态及待决问题；只做设计时，检查用户要求的草案或设计说明。如仍有实现项，记录交付及续接位置，将计划保留在 `active` 等待实施授权。
- 已获授权并实施的功能计划，当前规格书与计划的版本应和已确认组合一致。每个实现项都须通过独立审查和验收。整体审查须检查完整规格覆盖、跨项集成、回归及最终证据。后续改动影响到的项重新验收。
- 用户能理解交付内容、限制及遗留问题。审查通过不意味着已发布、合并或完成目标机器验收。

若有任务记录，主 agent 记录结果；满足验收条件后将其移至 `completed`。未结束的任务留在 `active` 并注明状态。功能规格书留在 `specs`，同步状态和计划链接；归档不使确认失效。记录代码提交及必要的数据版本。尚未提交时明确注明，并记录基线、改动摘要、证据及已有改动边界。原始日志、截图和其他验证产物存入 `test`；`harness` 的任务记录只保留摘要、引用和来源。

`harness` 与 `project/code` 分别进行版本控制。验收不自动授权提交、推送、合并、发布或破坏性操作；只在当前任务明确授权的范围内操作，并记录实际完成的交付阶段。
