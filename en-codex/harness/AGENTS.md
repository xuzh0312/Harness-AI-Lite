# Project Working Rules

## Starting a Task

Take on one **conversation role**.

1. Identify the user's current goal. Read the [project overview](README.md), [hot paths](docs/paths.md), [architecture and three-area boundaries](ARCHITECTURE.md), and rules for the target directory. Before creating the first implementer or reviewer, check the [project subagent agreement](agents/MODELS.md). If there is no applicable answer, ask about model and reasoning effort before dispatching work. Reuse an existing applicable answer. Interviews, planning, and Q&A that do not use subagents do not require this question.
2. Locate this feature's resume entry in hot paths. Check the actual files for scope, versions, status, user confirmation, and active writers. Templates, placeholders, old timestamps, and file existence do not establish that a step is complete. If the user gives no step number, infer it from the evidence: if only the interview and reference records are confirmed and the user asks to choose a stack, resume at step 2; if this feature already has an approved Plan and the user only asks for a review, review it without implementing. Read only the inputs needed for this step. Do not infer progress from a whole-repository scan, cold paths, or old chats.
3. Use the table below to select the role and step. If the prompt conflicts with the files, may refer to more than one feature, lacks a prerequisite decision, or leaves write ownership unclear, explain the specific conflict and ask the user one question that resolves it. Until then, do not overwrite, skip steps, or dispatch work. A review-only request calls for findings, without automatically taking over writes. If only the current step is delegated, stop at handoff.

| Step | Role that speaks directly with the user | Inputs and deliverable |
| --- | --- | --- |
| 1. Requirements and references | [Task Planner](agents/task-planner/AGENT.md) | Project overview or feature increment: keep an interview record during the discussion; decide with the user whether to research, and maintain a separate open-source reference record, including the reason if research is skipped |
| 2. Features and stack selection | Task Planner | The first two records and current project state: agree on concrete features and technology stack with the user and record them in one report |
| 3. UI/UX | [Interaction Planner](agents/interaction-planner/AGENT.md) | The three preceding documents: develop a UI/UX proposal with the user and dispatch an implementer to make a preview in test if needed. If the interface is unaffected, record the reason and confirmation without creating a draft |
| 4. Project proposal | Task Planner | Confirmed feature and technology stack report, and UI/UX proposal or a decision that UI/UX does not apply: produce a project proposal and check feasibility, conflicts, and verifiability |
| 5. Implementation Plan | Task Planner | Checked project proposal: create a numbered checklist, dependencies, write boundaries, per-item review criteria, and overall acceptance criteria; present the proposal and Plan versions for approval |
| 6. Execution | [Execution Coordinator](agents/execution-coordinator/AGENT.md) | Approved proposal and Plan **plus implementation authorization**: dispatch implementers and reviewers for each item, accept the work item by item, then run an overall dual review |

New projects and feature additions use the same handoffs. For an existing product, inspect its current state and plan only the increment, affected interfaces, and regression scope. If the stack or interactions stay the same, reference their valid versions and explain why they are unaffected. Steps can span sessions or continue in the same session; reusing a role does not expand the user's authorization. See [planning deliverables](docs/specs/README.md) for file locations.

## Writing, Authorization and Acceptance

- Conversation roles maintain deliverables within the scope of the current step. Multiple sessions may read the same version; each file, ID, or shared index has one writer at a time. Before a handoff, confirm that the previous writer has stopped or that its writes are isolated, and reread the actual file before editing. Losing contact does not establish that writes have stopped; the user's confirmation that the previous session was closed or invalidated does. Subagents report results and do not edit shared indexes, stage status, or approval records.
- Use a sibling `<original-filename>.lock` file to protect each shared file ([hot paths](docs/paths.md), [cold paths](docs/paths-cold.md), [bug knowledge base](docs/bugs.md), and [subagent agreement](agents/MODELS.md)), for example `docs/paths.md.lock`. All writers must operate on the same actual copy. Acquire the lock with an atomic create-only-if-absent operation such as `FileMode.CreateNew`. If the lock exists, do not write; do not check and create in separate operations or overwrite it. Put the unique session ID, scope, and start time in the lock. The `Current writer` field in the document is for handoff only. After acquiring the lock, reread the document, confirm there is no writer with an unfinished handoff, register yourself, make the change, and verify it. Reset the field to `None`, then remove only the lock you hold. Do not hold a lock while waiting for the user or commit it. Never clear a lock left by an interruption, even an empty one, or its writer entry based on a timeout. To recover, pause all competing writes to the file, verify that the old writer and any commands have stopped, and inspect unfinished changes. A single successor then clears and reacquires the lock. If you cannot verify this, lack permission to create the lock, or are on storage that does not guarantee atomic creation, stop writing and hand off. Stage deliverables and Plans record their writers in their handoff cards or resume entries.
- Check allowed writes and allowed checks separately and preserve the user's existing changes. Deliver read-only work in the conversation without assigning formal IDs or creating records. State `Not run` when checks are prohibited. Ask open questions about facts and experiences; offer alternatives and reasons for tradeoffs, one question at a time. Ask in the conversation when a tool is unsuitable.
- Of the [five roles](agents/README.md), only implementer and reviewer are subagents. When independent review is required, the conversation role responsible for submitting the work creates two read-only reviewers with independent contexts, one for specification compliance and one for quality. Both review the same final version. Apply the [dual review acceptance conditions](agents/reviewer/AGENT.md#findings-and-conclusions) to the original conclusions, required evidence, and remaining blocking findings. Refer unresolved disputes after rechecking to the user. If capacity is limited, run the two reviews sequentially and say so. Work is blocked if either reviewer is unavailable. Do not delegate recursively or use self-review as a substitute.
- Execute project features only under an approved Plan with implementation authorization. Code, infrastructure, and rule changes that affect later decisions require dual review. A standalone fix under an existing contract does not require inventing a new feature; see the [execution handbook](docs/runbooks/execution.md). For substantive changes, pause affected items, return them to the appropriate planner for revision, and recheck approval and implementation authorization.
- Keep management materials in harness, the software in project/code, and prototypes, tests, and raw evidence in test. Generate installers only within the [packaging boundaries](ARCHITECTURE.md). Moving a reference to cold paths does not authorize deletion. Acceptance does not automatically authorize packaging, commits, pushes, merges, or releases.
