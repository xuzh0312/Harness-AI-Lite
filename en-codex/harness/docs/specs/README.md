# Planning artifacts and cross-session handoff

One planning cycle covers an initial project release or one feature increment. Do not copy the whole set of artifacts for each session. These are **paths relative to harness**. Create them only in an actual project copy when writes for that step are authorized. `<ID>` is `PLAN-` followed by four digits. Step 1 uses this ID to link artifacts; it does not imply a Plan exists or implementation is authorized. See the [numbering rules](../plans/README.md) for reservation, reuse, and archiving.

| Step | File | Minimum content and handoff criteria |
| --- | --- | --- |
| 1 | `docs/specs/<ID>/interview.md` (interview record) | Who does what in which situation, problems and counterexamples, initial scope and non-goals, original user intent, decisions and open questions. Update the record when an answer affects the proposal, and check the summary with the user. |
| 1 | `docs/specs/<ID>/references.md` (open-source reference record) | Research decision and scope. For each candidate, record the source, fixed version, license evidence, parts considered, obligations or uncertainties, and whether to adopt, exclude, or defer it after discussion. Record why research was skipped or no candidate was suitable; do not invent results. |
| 2 | `docs/specs/<ID>/features-stack.md` (feature and technology stack report) | For each feature, record users, entry points, inputs and outputs, boundaries, exceptions, and success criteria. Include the current stack, alternatives and tradeoffs, what to keep, add, or replace, migration and compatibility impact, and user confirmation. Distinguish the report's decisions from architecture already in effect. |
| 3 | `docs/specs/<ID>/uiux.md` (UI/UX proposal) | Use the three earlier files to record flows, key states, feedback, error recovery, acceptance checks, selected design version, and user feedback. If there is no UI impact, record scope, reason, and user confirmation; no mockup is required. |
| 4 | `docs/specs/<ID>.md` (project proposal, used as the implementation specification) | Use the [proposal template](TEMPLATE.md) to consolidate confirmed decisions and reference input versions. Explain how modules, data, and interfaces support goals, risks, and ACs. Record feasibility findings, corrections, and decisions still needed. Do not break down implementation work while major conflicts remain unresolved. |
| 5-6 | `docs/plans/active/<ID>.md` (implementation Plan) | Use the [Plan template](../plans/TEMPLATE.md) to map proposal ACs to verifiable numbered items. In step 5, record approval of the combination and implementation authorization status, which may be unauthorized. Use the same file to track execution and acceptance in step 6. |

**Each artifact starts with its own handoff card:** feature ID and scope; step, document version, and status (draft, awaiting confirmation, confirmed, or needs review; give the basis when a step is skipped); input files and versions; what the user confirmed and the evidence for it; unresolved matters or blockers; current writer or confirmation that writing has stopped; and the next step and owner. Use existing fields where possible. For the Plan, use the resume entry at the top. The two step 1 records track interview and research status separately. Update the card when a decision takes effect, work is interrupted, or a handoff occurs. Do not wait until the end of the conversation to reconstruct it from memory. A missing file, a draft, and an explicit user decision to skip are distinct states.

Register the feature's current entry point in the [hot paths](../paths.md). The artifact itself is authoritative for status and authorization; do not duplicate approval records in the index. In a new session, use both the request and the files to determine the state. Another task planner may review the same report read-only. If an input version changed, compare the changes first, mark only affected downstream conclusions for review, and ask the relevant role and user to confirm them; do not redo unaffected work. The conversation role changing an upstream decision records the new and previous versions and the affected scope in its own artifact. Update the hot entry in serial order to point to this change, or hand it to the current index writer. Notify active writers to stop dispatch or writing. If work is already in implementation, do not change the Plan without authorization or treat sending a notice as confirmation that writing has stopped. Without index write permission, hand over pending index changes in the reply and identify anyone still to be notified. For read-only work, provide the same handoff fields in the reply without claiming they were saved.
