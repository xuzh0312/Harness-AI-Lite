# Development and test materials

Keep development and verification materials outside the software itself in this area. Create directories as needed; do not precreate fixed subdirectories:

- **Versionable source:** `test/src/` is a reserved entry, created as needed, for test and helper-tool source confirmed suitable for sharing. No `.gitignore` change is needed.
- **Shareable approved designs:** `test/approved-designs/` is created as needed and eligible for Git tracking by default. Store only selected versions authorized for sharing and their necessary resources.
- **Other persistent materials:** sample data, draft designs, and sanitized verification evidence belong outside those two entries and are ignored by default. A small number of authorized, shareable files may be individually allowed.
- **Disposable output:** caches, ordinary build output, intermediates, raw logs, screenshots, recordings, and temporary experiments belong outside those entries, separate from persistent material, and are ignored by default.

Before using a selected design as an approval basis, verify that it and its necessary resources can be restored from a specific test repository commit or an authorized controlled backup. Record it in the UI/UX proposal in step 3; from step 5 reference it in the PLAN, or in the TASK for independent work. Record its path relative to test, commit or backup version, content checksum, and recovery location. Designs containing sensitive information or large files remain in the ignored area by default and use an authorized controlled backup. If only a working-tree file or checksum exists, first obtain retention authorization, or ask the user to confirm independently verifiable written requirements in the specification or task record as the basis. Before approval, initial dispatch, and resumed implementation, retrieve the fixed version and required resources and verify their checksums. If unavailable or mismatched, pause dependent approval and implementation until the original is restored or the user confirms an independent written basis. Reconfirm affected scope when a changed design changes acceptance criteria.

This area is an independent test Git repository, rooted at test. Verify that source and materials to retain are tracked by that repository; use a controlled backup and record its location and recovery method when not tracked or unsuitable for Git. If the repository is not initialized, report it and wait for authorization; do not initialize it yourself. Commits also require authorization. Unclassified files go outside the two entries above and are ignored by default. Large files and sensitive data are not committed or distributed by default; retention and backup require authorization. Preserve the tracking status of existing tests during integration; do not clean them up without authorization.

When running tests, specify the actual software and test paths. Persistent evidence identifies the code version (for uncommitted work, the baseline and validated working-tree scope), and artifact identifiers when needed. Task records reference evidence relative to the test root without exposing sensitive names. Keep brief task and bug records in harness. Follow harness/ARCHITECTURE.md for final ZIP authorization, location, and independent verification. Report conflicts when a tool cannot comply with these boundaries.
