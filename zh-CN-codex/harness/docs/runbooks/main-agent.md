# 主 Agent 执行与验收手册

本手册定义通用行为协议，无后台调度器或原生配置。入口为 [AGENTS.md](../../AGENTS.md)，角色职责以 [角色协议](../../agents/README.md) 为准，模型配置仅以 [MODELS.md](../../agents/MODELS.md) 为准。

## 1. 入口确认与任务记录

读取 Harness 入口、[路径表](../paths.md)及目标目录适用规则。确认三域实际位置、读取与写入权限、任务授权、当前代码状态及已有改动。路径未提供但能由当前工作区可靠确定时先检查；不使用的区域注明不适用，确有缺失且影响工作时再询问。

工作目录、规则加载与访问权限分别确认。Harness 是管理依据，执行目录按任务选择；业务命令通常在 project/code 执行，项目文档任务在 harness 执行。不可因工作区同时打开多个目录就认为它们共用仓库或权限。

除用户选择直接修改的功能任务外，需要分派或持续跟踪的任务，使用 [计划模板](../plans/TEMPLATE.md) 在 active 下建立唯一任务记录；选择功能设计规划时由 feature-plan 直接创建这份记录，不提前另建一份。已有记录则先核对实际文件和证据再续接，不从头重做。纯问答与轻微文字调整无需生成正式计划，但仍需说明适用的验证结果。只有主 agent 更新共享记录和状态。

## 2. 定义验收并选择角色

先记录目标、非目标、允许修改范围、预期行为及其验证方式。按 ARCHITECTURE.md 核对每类文件的存放位置：软件本体在 project/code，测试和辅助代码等在 test，harness 仅保留管理资料。关键需求未决时先澄清；不影响目标的实施细节选择最小方案并记录理由。

新功能及功能增强由用户选择功能设计规划或主 agent 直接修改，不推荐其中一项。选择直接修改时按授权执行，无需新建功能规格书与实现计划。选择规划时读取 [feature-plan](../../.agents/skills/feature-plan/SKILL.md)：缺少项目介绍时请用户提供。技术栈已选但未记录时请用户提供；尚未确定时按 [tech-stack-plan](../../.agents/skills/tech-stack-plan/SKILL.md) 与用户规划，只更新项目介绍与技术栈架构文档，随后重读两份文档。主 agent 逐题访谈并同步整理规格草案，检查需求覆盖后生成编号实现清单。规格书与计划共用功能编号、分别版本化，一起展示给用户确认。此前仅进行调研、讨论和规划文档编写，不启动有依赖的实现；局部回答不等于整体批准。确认后在原计划记录执行进度；实质变更回到 feature-plan 修订并重新确认组合。其他任务沿用适用流程，不强制新建功能计划。

| 任务条件 | 调用角色与顺序 |
| --- | --- |
| 纯问答、轻微文字调整 | 主 agent 直接完成并检查 |
| 范围明确的小型代码修复 | implementer → 两个 reviewer 并行审查 → 主 agent 验收 |
| 用户选择直接修改功能 | 主 agent 修改 → 按改动类型完成适用的独立审查与验证 → 主 agent 验收 |
| 用户选择功能设计规划 | 主 agent 访谈并维护规格与计划 → 用户确认组合 → 执行技能逐项派工、审查、验收 → 整体审查与主 agent 验收 |
| 非新功能任务中的跨模块或重要接口决策 | 主 agent 分析并核对需求与授权 → implementer → 两个 reviewer 并行审查 → 主 agent 验收 |
| 需要交互式界面设计 | UIdesign 与用户讨论设计，再向主 agent 交接 |
| 环境、脚本、CI、构建或打包 | implementer → 两个 reviewer 并行审查 → 主 agent 验收；有重要设计决策时由主 agent 先分析 |
| 影响后续决策的规则变更 | 主 agent 或 implementer 修改 → 两个 reviewer 并行场景审查 → 主 agent 验收 |
| 代码与基础设施混合任务 | 有依赖先完成前置项，无依赖且写入互斥时可分派给独立的 implementer 实例；整合后两个 reviewer 并行审查 |

不为凑齐三角色创建无实际任务的子 agent。凡需独立审查，主 agent 都派 reviewer-spec 与 reviewer-quality 两个独立实例，分别负责规格符合性与实现质量，均读取 MODELS.md 的 reviewer 配置。没有功能规格书时，审查的规格依据是任务要求和既有契约，不强制新建规格书。代码、基础设施和决策性规则改动缺少任一报告时属于验收阻塞，不以作者自审或一个实例兼任替代。

上表混合任务的实现并行安排仅适用于非功能任务。已批准功能计划使用 [subagent-driven-execution](../../.agents/skills/subagent-driven-execution/SKILL.md)：每项新的 implementer 上下文只承担当前项，依次完成实现、自审、两个 reviewer 并行审查、返工复验与主 agent 验收，再开始下一实现项；必要只读调查可并行。全部实现项通过后新建两个 reviewer 做一次整体审查。

## 3. 分派与整合

使用 [交接模板](../../agents/TASK_TEMPLATE.md)，传入明确路径、基线、写入范围、依赖、验收与角色配置。每次创建前重读 MODELS.md 的对应角色并显式设置模型和深度；仅在工具要求时使用可支持显式配置的全新上下文方式，例如 fork_turns=none，完整提供必要任务材料。不让角色依赖未传入的聊天记录。

不超过运行器并发上限；容量不足时两个 reviewer 保留独立上下文顺序完成，并记录实际未并行；不能降为单 reviewer。其他任务容量不足时同样顺序执行。不并行写相同文件，不让子 agent 嵌套派生。主 agent 也不在执行者工作期间修改其分配文件。关键设计决策尚未确认时，不启动依赖该决策的实现。

收到返回后核对真实文件、改动范围、结果与证据，不能只转述子 agent 的“完成”。共享任务记录由主 agent 汇总；角色设计与审查默认只读。发现越界改动时先识别来源，不覆盖或撤销用户既有内容。

已批准功能计划的简报、执行者身份、派工前基线、交付及审查摘要、返工轮数与下一步集中在原计划，不另建进度台账。派工只传本项、必要接口、前置结果和全局约束，不复制整段聊天。原始差异、未提交内容的前置快照及验证产物放 test，harness 仅保留管理摘要和引用；未提交状态也必须覆盖完整任务差异，不能只看 HEAD~1。

## 4. 审查、返工与阻塞

向两个 reviewer 提供同一目标、要求来源、验收、方案、受审版本、完整任务差异、执行者报告及证据，各自独立形成初次判断。未提交时提供文件范围和工作树状态，不用不存在的提交 SHA 冒充版本基线。两份报告返回前保持受审版本不变；外部变更使其改变时更新输入并复核，不混用版本。

两实例各自按负责维度返回建议通过／需返工／证据不足，注明实例身份、维度、轮次、覆盖版本及证据，主 agent 保留两份结论。只有两份均建议通过且覆盖同一最终版本、必要证据齐全才验收；任一缺失或未通过都不能勾选完成。冲突按证据裁定，不投票、不互相抵消；重复发现保留两个来源后去重。返工优先恢复原执行者与本组两个 reviewer，无法恢复或角色配置变化时按最新配置新建并交接。同版本证据仍有效时不机械重跑检查。

同时提供 [bug-detect 技能](../../.agents/skills/bug-detect/SKILL.md)和 [项目错误知识库](../bugs.md)。reviewer 发现缺陷或复验时调用技能，返回查询和记录提议；主 agent 写前重读最新知识库，按根因去重并串行分配编号或更新原条目。并行 reviewer 不直接写入。同类复发重新打开原记录，保留已验证方案的适用范围；没有新信息则不更新。

修复任务向 implementer 提供相关 BUG 条目，但不得未经核对直接套用旧方案。复核后由主 agent 补充实际解决方案与证据，满足关闭条件才改为已解决。知识库不可写时返回未落盘提议并记录具体阻塞，不能声称已保存；强制审查与验证照常执行。任务记录只引用最终 BUG ID，避免重复保存完整条目。

对每项发现明确接受修复或有依据地拒绝，由主 agent 记录裁定。验收标准本身需要改变时回到需求确认；不通过删除检查或降低标准掩盖失败。执行者修复后重跑受影响检查，两个 reviewer 分别复核相关发现、新差异及最终版本；本维度无变化时可以复用有效证据，但需明确核对当前版本，再由主 agent 验收。复验边界以 [reviewer 协议](../../agents/reviewer/AGENT.md) 为准。

连续两轮返工出现同一问题且无新证据时，主 agent 重新分析根因、方案和分派方式，不继续机械重试；需要用户决策时只提出具体未决事项。此规则不等于自动停止所有有进展的修复。

缺少必要权限、依赖、外部服务、关键需求或强制审查能力时记录具体阻塞、已尝试操作、影响和恢复条件。继续不依赖该条件的已授权工作；条件恢复后从记录位置续接，并核对已有证据是否仍有效。

## 5. 最终验收与状态

| 状态 | 进入条件 |
| --- | --- |
| 待处理 | 已有目标，尚未开始执行 |
| 待确认 | 功能规格与计划草案已生成或修订，等待用户确认当前组合；不得开始依赖实现 |
| 执行中 | 入口确认后开始分析、设计或实现 |
| 验收中 | 交付可检查，正在审查或核对证据 |
| 返工 | 存在必须修复的发现，已分派处理 |
| 受阻 | 缺失外部条件或关键决策，阻塞部分有明确恢复条件 |
| 完成 | 目标范围、适用检查、强制审查和最终验收全部满足 |
| 已取消 | 用户取消任务，注明取消原因后归档，不代表已实现 |

状态由主 agent 按实际情况更新；功能文档组合获用户批准且有实施授权后才进入实现，实质修订回到待确认；纯规划批准不触发实施。返工修复后回到验收中，受阻解除后回到对应环节；不能越过尚未满足的用户确认。子任务“已完成”不能直接把主任务置为完成。

完成前逐项确认：

- 最终差异符合任务范围，用户既有改动得到保留；新增文件符合三域边界，未要求打包时没有生成安装包。
- docs/paths.md 的路径表与当前实际目录树已核对，包含任务产生的结构变化；未能核对的区域明确说明，不能冒充同步完成。
- 每项必需验收有证据，或具有合理的不适用说明；必需检查失败、未运行、关键证据缺失均不能标为通过。
- 证据写明工作目录、检查方式、结果和覆盖版本或工作树范围；受后续改动影响的结论已经重新验证。不重复运行仍有效的无关检查。
- 所有阻塞发现已修复并复核，或有符合已确认需求的明确裁定；不能将未满足的需求裁定为通过。
- 所有强制审查范围均有两个独立实例的报告，分别覆盖规格符合性和实现质量，结论均建议通过且对应同一最终版本；容量不足的顺序审查如实记录，不冒充并行。
- 采用功能设计规划时，功能规格与计划的当前版本匹配批准组合，所有实现项已逐项独立审查验收，且全功能的规格覆盖、跨项集成、回归和最终证据已通过一次整体审查；后续修改影响的条目已重新验收。
- 用户可理解交付结果、限制与剩余问题。审查通过不代表发布、合并或目标机器验收已发生。

已有任务记录时，由主 agent 填写结果并在完成后移至 completed；未满足条件的任务保留 active，并注明状态。功能规格保留 specs 原位，更新状态及计划链接，归档移动不使批准失效。记录代码提交和必要的数据版本；尚未提交时写明“未提交”，记录基线、改动摘要、证据与已有改动边界。原始日志、截图和其他验证产物均保存在 test，harness 的任务记录仅保留摘要、引用及来源。

harness 与 project/code 分别版本控制。验收通过不自动授权提交、推送、合并、发布或破坏性操作；按当前任务明确授权执行，记录实际完成的交付阶段。
