# Apple 设计

Apple 如何打造这样的界面：不再让人感觉是在操作一台计算机，而开始像自身的延伸。这些知识来自 Apple 的 WWDC 设计演讲，主要是 *Designing Fluid Interfaces*（WWDC 2018），并被提炼、转译到 Web 平台（CSS、Pointer Events、`requestAnimationFrame`、Motion／Framer Motion 等弹簧库）。

贯穿始终的主线是：**当运动从当前屏幕上的值开始、继承用户的速度、向前投射惯性，并且能在任何瞬间被抓住和反向时，界面就会显得有生命。** 弹簧是实现这一切自然感的工具，因为它天然可中断，并且感知速度。

## 核心理念

> “当我们让界面与思考和运动的方式一致时，奇妙的事情就会发生——它不再像一台计算机，而开始像我们自身的无缝延伸。”

当界面像物理世界一样运作时，它才是流畅的：即时响应、连续移动、携带惯性、在边界产生阻力，并且能在运动途中改变方向。下文所有内容都是朝着这个目标靠近的方法。

Apple 把设计视为服务四种人类需求：**安全与可预测性、理解、成就感和愉悦感。** 这里的每条规则都服务于其中之一。

## 1. 响应 — 消除延迟

一旦出现延迟，直接感就会“悬崖式下跌”。响应是其他一切体验的基础。

- **在 pointer-down 时响应，而不是等到 pointer-up。** 按钮一被按下就高亮。等到 `click`／触摸抬起后才显示反馈，会让人感觉像死掉了。
- **警惕每一处延迟。** 审查防抖、人为计时器、过渡等待和约 300ms 的点按延迟。输入路径上任何非必要的等待都是退化。
- **反馈必须在交互*过程中*连续出现，不能只在结束时出现。** 对于拖动、滑块或抽屉，整个过程中要让 UI 与指针保持 1:1 更新——绝不要只在手势结束时才播放动画。

```css
/* 反馈发生在按下时，而且是即时的 */
.button:active {
  transform: scale(0.97);
  transition: transform 100ms ease-out;
}
```

## 2. 直接操纵 — 1:1 跟踪

> “触摸与内容应当一起移动。”

用户拖动某物时，它必须紧贴手指，并尊重用户*抓住它时*的偏移位置。抓取瞬间跳到元素中心，会立刻破坏这种错觉。

- 使用 Pointer Events 与 `setPointerCapture`，即使指针离开元素边界，也能继续跟踪。
- 记录一小段**速度／位置历史**（最近几次 `pointermove` 事件），而不只是当前点——松手时会需要速度。

```js
el.addEventListener('pointerdown', (e) => {
  el.setPointerCapture(e.pointerId);
  const grabOffset = e.clientY - el.getBoundingClientRect().top; // 尊重用户抓住的位置
  // ...track position + timestamp history for velocity
});
```

## 3. 可中断性 — 最重要的单一原则

> “思考与手势是并行发生的。”

每个动画都必须能在任何时刻被中断并改变方向。用户必须能在运动途中抓住一个正在移动的元素并反向，而不必等待动画播放完毕。一个正在关闭的模态框如果再次被用户抓住，应当跟随手指——而不是先完成关闭，再重新打开。

- **绝不要在过渡期间锁定输入。**
- **始终从*呈现*（当前）值开始动画，绝不要从目标值开始。** 中断时读取元素屏幕上实时的 transform，并从那里开始新动画。从逻辑值／目标值开始会导致可见跳变。
- **手势驱动的内容应避免 CSS transitions 和 `@keyframes`**——它们无法在运动途中被平滑抓住和反向。弹簧默认从当前值开始动画，正好适合中断。
- **手势反向时，要混合速度——不要硬切。** 在反向时用一个动画替换另一个动画会造成速度不连续，形成一堵“砖墙”。能够通过重新设定目标来保留速度的弹簧库可以避免此问题。（这正是 iOS 原生 *additive animations* 所做的事；在 Web 上，应选择能从当前速度重新设定目标的弹簧库。）
- **把二维运动拆成独立的 X、Y 弹簧。** 对二维距离只使用一个弹簧时，如果 X、Y 速度不同，运动会失去同步。

## 4. 行为优先于动画 — 使用弹簧

> “把动画看作你与对象之间的对话，而不是界面事先规定好的东西。”

预先编排、固定时长的动画无法响应新输入。弹簧可以——新输入只需改变目标，运动仍保持连续。只要用户能触摸，就优先考虑弹簧。

Apple 有意用两个便于设计师理解的参数替代了物理三要素（质量／刚度／阻尼）。应围绕这两个参数思考：

- **Damping ratio（阻尼比）**——控制过冲。`1.0` 表示临界阻尼，不回弹，平滑停止。`< 1.0` 表示会越过目标并振荡。数值越低，回弹越明显。
- **Response（响应）**——数值以秒为单位达到目标的速度。数值越低越干脆。**它不是“时长”**——弹簧没有固定时长；其停止时间由参数自然产生。

**默认值：**
- 大多数 UI 从**阻尼 `1.0`**（临界阻尼）开始——优雅且不分散注意力。
- **仅在手势本身携带惯性时**（快速甩动、投掷、拖动松手）增加回弹（**阻尼约 `0.8`**）。一个刚刚淡入的菜单若发生过冲，会显得不对；被快速甩出的卡片发生一点过冲，则很自然。

**Apple 实际采用的数值：**

| 交互 | 阻尼 | 响应 |
| --- | --- | --- |
| 移动／重新定位（例如 PiP） | `1.0` | `0.4` |
| 旋转 | `0.8` | `0.4` |
| 抽屉／面板 | `0.8` | `0.3` |

**Web 映射（Motion／Framer Motion）：** `bounce` + `duration` 的弹簧 API 与 Apple 的阻尼 + 响应较为接近。一个安全的通用风格是默认处处使用 `damping: 1.0` 的弹簧；只把回弹留给由惯性驱动的物理交互。

```js
import { animate } from 'motion';

// 临界阻尼默认值（无过冲）
animate(el, { y: 0 }, { type: 'spring', bounce: 0, duration: 0.4 });

// 惯性交互——只因为此前有快速甩动，才加入一点回弹
animate(el, { y: target }, { type: 'spring', bounce: 0.2, duration: 0.4 });
```

## 5. 速度交接 — 拖动与动画之间的接缝

手势结束时，动画必须**以手指的准确速度继续**，这样拖动与动画之间就不会出现可见接缝。正是这个细节，最能区分“流畅”与“还行”。

把指针松手时的速度作为弹簧的初速度传入。有些弹簧 API 需要**相对**速度，可按到目标的剩余距离归一化：

```
relativeVelocity = gestureVelocity / (targetValue − currentValue)
```

示例：元素位于 `y=50`，目标为 `y=150`（还差 100px），手指以 50px/s 移动 → 弹簧初速度 = `50 / 100 = 0.5`。Framer Motion／Motion 直接接受绝对 px/s 速度（`velocity` 选项），所以通常应传入原始值。

## 6. 惯性投影 — 动画到手势*将要去的*位置

> “用小的输入产生大的输出。”

不要从*松手点*吸附到最近的边界。应使用速度**预测静止位置**——完全像滚动减速那样——然后吸附到距离该预测点最近的目标。正是这一点，让快速甩动感觉像是在把元素抛出去。

Apple 的精确投影函数（来自 *Designing Fluid Interfaces* 示例代码）：

```js
// decelerationRate ≈ 0.998 表示正常滚动手感；0.99 更干脆
function project(initialVelocity /* px/s */, decelerationRate = 0.998) {
  return (initialVelocity / 1000) * decelerationRate / (1 - decelerationRate);
}

const projectedEndpoint = currentPosition + project(releaseVelocity);
const target = nearestSnapPoint(projectedEndpoint);   // 根据投影结果选择目标
animateSpringTo(target, { velocity: releaseVelocity }); // 然后交接速度（§5）
```

注意：物理教科书里的 `v²/(2·decel)` *不是* Apple 实际采用的公式——应使用上面的指数衰减形式。优秀的底部面板和轮播组件（Vaul、Embla）采用的都是这种标准行为。

## 7. 空间一致性 — 对称路径、锚定原点

> “如果某物以一种方式消失，我们会期待它从来的地方出现。”

- **沿同一路径进入和退出。** 从右侧滑入的面板必须向右侧关闭。从右进、从下出会显得割裂且令人困惑。
- **把交互锚定到来源。** 菜单、浮层或面板应从触发它的元素处出现——设置 `transform-origin` 指向触发控件，这样按钮与内容之间的空间关系才明显。（这与前面的浮层缩放点相同：应从触发控件缩放，而不是从中心缩放。）
- **可逆过渡要镜像缓动**，使出程与回程匹配（两个方向使用互为反向的三次贝塞尔控制点）。

## 8. 沿手势方向给出提示

人类会根据轨迹预测最终状态。中间的运动应预示事物将去往何处——控制中心的模块会“向手指方向向上、向外生长”。让中间帧指向结果，而不是盲目插值到结果。

## 9. 橡皮筋回弹 — 柔和边界

到达边缘时，应逐步增加阻力，而不是硬性停止。硬停读作“冻住了”；连续阻力读作“仍能响应，但这里没有更多内容了”。用户拖得越远，施加的阻尼越大。

```js
// 越过边界越远，元素跟随得越少——现实中的物体也会在停下前减速
function rubberband(overshoot, dimension, constant = 0.55) {
  return (overshoot * dimension * constant) / (dimension + constant * Math.abs(overshoot));
}
```

## 10. 手势设计细节（“手感”检查表）

- **点按：** 在触摸*按下*时立即高亮，在触摸*抬起*时提交。目标周围增加约 10px 的迟滞／命中填充，并允许拖离后再拖回以取消。
- **拖动／滑动：** 在确定方向前要求很小的移动阈值（迟滞，约 10px），确定后再进行 1:1 跟踪。
- **从第一次移动开始并行识别所有可能的手势**，意图明确后再果断取消落败者。避免只报告*最终*状态的识别器（`swipeleft` 一类事件）——它们会丢弃反馈所需的连续跟踪。
- **尽量减少消歧延迟。** 双击检测不可避免地会延迟单击；只在双击确实存在的地方付出这项成本。

## 11. 帧级流畅性

流畅性关乎*帧里有什么*，而不只是帧率。

- 使逐帧位置变化低于感知阈值，避免拖影。
- 对于非常快速的动作，细微的**运动模糊／拉伸**能表达速度，比硬而锐利的拖尾更好看。
- `requestAnimationFrame` 是 Web 与显示同步的时钟（Apple 使用 `CADisplayLink`）。只动画合成器友好的属性——`transform` 和 `opacity`——并在即将运动时用 `will-change` 提示浏览器。

## 12. 材质与纵深 — 半透明传达层级

Apple 把半透明材质用作浮动的功能层，带来结构感但不抢走焦点。在 Web 上，可用 `backdrop-filter` 近似实现。

- **把导航栏、工具栏和面板构建成半透明层**（`backdrop-filter: blur()` + 半透明背景），内容从下方滚动——而不是占用固定条带的不透明栏。
- **材质厚度编码层级：** 更暗／更重的材质分隔结构区域（侧边栏）；更轻的材质吸引注意交互元素（按钮）。**绝不要在一个半透明浅色表面上再叠一个**——可读性会崩塌。
- **更大的表面应读起来更厚：** 使用比小标签更强的模糊 + 更深的阴影。可以考虑感知上下文的阴影——在繁忙／文本内容上方使用更重的效果以便分隔，在朴素背景上方使用更轻的效果。
- **变暗以聚焦，分隔以保持心流。** 模态任务把表面与变暗遮罩搭配，并把背景后推／下沉。并行的非阻塞面板使用半透明和偏移，但*不用*遮罩，这样心流不会被打断。对于堆叠面板，逐层让每个父层变暗并后退。
- **活力效果让文字在变化的背景上仍保持可读。** 在模糊／半透明表面上，不要使用扁平灰色文字——应提高对比度、稍微加粗字重，并略微增加字距。颜色应放在实色层上，而不是半透明前景上。
- **使用滚动边缘效果，而不是硬分隔线。** 不要在吸顶标题下加 1px 边框，而应在内容与浮动界面元素相交处淡入一小块模糊／渐变遮罩——只在浮动 UI 确实覆盖内容的地方这样做。
- **材质化，不要只是淡化。** 对于玻璃／模糊表面，进入／退出时同时动画模糊半径与缩放，使表面读起来像真实材质抵达，而不是普通的透明度淡入。

```css
.toolbar {
  background: rgba(255, 255, 255, 0.6);
  backdrop-filter: blur(20px) saturate(180%);
  border-top: 1px solid rgba(255, 255, 255, 0.4); /* 明亮的顶边 = 光线打在材质上 */
}
```

## 13. 多模态反馈 — 运动 + 声音 + 触觉

组合多种感官的三条规则（来自 *Designing Audio-Haptic Experiences*）：

1. **因果性**——必须明显看出反馈由什么引起。在实际的因果事件上触发（开关翻转、项目吸附到位），并让反馈特征与动作的物理感匹配。
2. **和谐性**——视觉、声音和触觉必须在**同一帧**触发。它们之间的延迟会破坏错觉。不要让 CSS 过渡拖慢音频／触觉（Vibration API）反馈。
3. **实用性**——只在值得的地方添加反馈。把触觉／声音留给有意义的时刻（成功、错误、提交、吸附）。反馈过多会让用户学会忽略全部反馈。

## 14. 减少动态效果与无障碍

减少动态效果并不意味着*没有*反馈——而是提供更温和、不引起前庭不适的等价反馈。响应三个独立信号，并把它们内置到组件中：

- **`prefers-reduced-motion: reduce`**——把滑动／弹簧／视差替换为简短的透明度**交叉淡化或静态过渡**。去除弹性／过冲。保留有助于理解的透明度／颜色变化。
- **`prefers-reduced-transparency: reduce`**——让半透明表面更雾化／更实：提高背景不透明度，去掉模糊。
- **`prefers-contrast: more`**——使用近乎实色的背景，并加上明确、有对比度的边框。

另外：避免全视口移动背景、缓慢循环的振荡运动（接近 0.2 Hz／每 5 秒一个周期）和突兀的亮度跳变（让深色↔浅色主题切换使用缓动）。让大型移动物体在移动过程中保持半透明，并在大范围重新定位时淡出大表面，停稳后再淡入。

```css
@media (prefers-reduced-motion: reduce) {
  .sheet { transition: opacity 200ms ease; transform: none !important; }
}
@media (prefers-reduced-transparency: reduce) {
  .toolbar { background: white; backdrop-filter: none; }
}
```

## 15. 字体排印 — 光学尺寸、字距、行距

Apple 设计字体时会随尺寸改变字形；同样的原则也适用于 Web。（来自 *The Details of UI Typography*，WWDC 2020。）

- **Tracking（字距）与尺寸相关——绝不要所有尺寸都用同一个值。** 大型展示文字需要*负*字距（文字变大后，字母会显得离得太远）；小号文字需要轻微*正*字距，以提高可读性。固定 `letter-spacing` 必然在某些地方不合适。标题收紧，正文接近 `0`。
- **行距（line-height）与字号反向变化。** 大标题使用紧行距，正文使用较松行距。对于高升部／高降部的文字脚本，增加行距；对于信息密集的 UI，收紧行距。
- **把字重 + 尺寸 + 行距作为一组来构建层级，** 而不是只看尺寸。用字重强调——它能增加存在感，但不占用更多空间。
- **尊重用户的文字尺寸设置**（Dynamic Type）。让布局*随*文字缩放——间距使用 `rem`／`em`，不要使用固定 px——这样更大的字体不会破坏布局。
- **优先使用平台的系统字体**，再考虑自定义字体；系统字体已经带有光学尺寸、字距表和可读性调优。只有有理由时才覆盖。

```css
:root { font: 100%/1.5 system-ui, sans-serif; } /* 正文：系统字体，舒适的行距 */

.display {
  font-size: clamp(2rem, 5vw, 4rem);
  line-height: 1.05;        /* 大字号使用紧行距 */
  letter-spacing: -0.02em;  /* 字号变大时使用负字距 */
  font-optical-sizing: auto;
}
```

## 16. 设计基础 — 八项原则

上面的运动与工艺服务于 Apple 的八项设计原则（*Principles of Great Design*，WWDC 2026）。思考时可用这些名称：

1. **目的。** 有意图地创造；决定*不*构建什么。每项功能都会索取用户的时间、注意力和信任——只把这笔预算花在有回报的地方。
2. **自主性。** 让用户保持控制：提供选择，不要强迫单一路径。用宽容来支撑——对误操作提供便捷撤销，只对真正具有破坏性、不可逆的操作使用确认对话框（谨慎使用；滥用会让用户养成盲目点击的习惯）。
3. **责任。** 以用户利益行事。隐私：在合适的时机询问，只请求必要信息，并保持透明。安全：预见误用与伤害——尤其是 AI（一个关注过敏的食谱应用绝不能建议有害食材）。增加预览、确认、免责声明；如果某项功能的风险大于价值，就删掉它。
4. **熟悉感。** 建立在用户已知事物之上。使用既不过于字面、也不过于抽象的隐喻（垃圾桶表示删除），并尊重其物理规律。保持一致：看起来相同的事物必须行为相同，并出现在同一位置（macOS 的关闭始终在左上角），这样用户才能预测接下来会发生什么。只有能证明新方式更好时，才打破熟悉的模式——然后要测试，不要假设。
5. **灵活性。** 为不同情境、设备和完整的能力范围而设计。适应平台（iPhone = 快速触摸；桌面 = 借助精确指针控制的深度工作流）和具体情境。采用包容性设计（年龄、语言、专业水平、无障碍）。当单一布局无法适合所有人时，让用户个性化——重新排列控件，隐藏他们不用的内容。
6. **简洁——不是极简。** 去掉不必要的内容，让核心目的闪耀；把所有东西都塞在一个地方看起来极简，但并不简洁。保持精炼（平实语言、不用术语、更少步骤）和清晰（利用层级——顺序、间距、对比——让最重要的内容最明显）。每个元素都要证明自己的位置；有时*添加*上下文反而能简化（例如显示剩余时间的视频进度条）。先展示常用路径，把高级选项放在下一层。
7. **工艺。** 对细节毫不妥协的关注能建立信任。精美的字体排印、适应明暗主题的颜色、清晰的图标，以及能即时给出自然反馈的响应式动画。没有任何随机——每个间距、时长和对齐值都是有意识且可辩护的选择。滚动抖动、图标错位、旋转后布局破损，都会被读作粗心。工艺需要迭代和长期维护——随着功能和硬件变化持续演进设计。
8. **愉悦。** 是做好前七项的结果，而不是额外撒上的彩纸。决定希望用户感受到的情绪（平静、自信、兴奋），并在每个决策中强化它。

服务于这些原则的战术规则：

- **反馈有四种：** 状态、完成、警告、错误。确认有意义的操作，展示持续状态，在问题发生前警告，就地验证（不在提交时）。
- **寻路。** 每个屏幕都应回答：我在哪里？我能去哪里？那里有什么？我怎么离开？绝不要把用户困住。
- **分组与映射。** 邻近意味着有关系；把控件放在它影响的对象附近，并让控件的排列镜像它所改变的内容。如果需要标签解释一个控件，映射关系就很弱。
- **直接、具体的标签胜过安全而笼统的标签。** 用内容命名导航项（“进度”“资料库”），不要用模糊的大类名（“首页”）。具体性创造可预测性。

## 17. 过程

- **交互式地进行原型设计——一个可交互的演示胜过“一百万张静态设计”。** 通过构建和试用发现界面；可用的原型还会设定明确标准，防止最终实现变得平庸。
- **同时设计交互和视觉。** “你应当看不出两者的界线在哪里。” 运动不是像素完成后再加上的图层。
- **在真实情境中与真实用户测试**，并用新鲜的眼光检查运动——慢放／逐帧播放，捕捉全速播放时看不见的问题。

| 需求 | 技术 | 具体值 |
| --- | --- | --- |
| 默认 UI 弹簧 | 临界阻尼，不过冲 | `damping 1.0`、`response 0.3–0.4` |
| 惯性／甩动弹簧 | 欠阻尼，轻微回弹 | `damping ~0.8`、`response 0.3–0.4` |

| 快速甩动的落点 | 投影惯性 | `current + (v/1000)·d/(1−d)`，`d ≈ 0.998` |
| 干净地中断 | 从呈现（实时）值开始 | 读取屏幕上的 transform |
| 避免反向时形成“砖墙” | 通过重新设定目标保留速度 | 混合速度的弹簧 |
| 可逆过渡 | 镜像缓动曲线 | 反向三次贝塞尔 |
| 决定反向还是提交 | 使用速度**符号**，而不是位置 | 松手时 |
| 1:1 拖动 | Pointer Events + capture | 尊重抓取偏移 |
| 反馈 | 在 pointer-down 时、持续反馈 | 绝不只在结束时反馈 |
