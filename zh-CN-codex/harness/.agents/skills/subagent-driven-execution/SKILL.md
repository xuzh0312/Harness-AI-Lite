# Subagent Driven Execution：逐项派工与独立验收

主 agent 读取当前规格书、计划和 [主 agent 手册](../../../docs/runbooks/main-agent.md)，按“单项实现 → 两个并行 reviewer 独立审查 → 返工复验 → 主 agent 验收”循环执行，最后由新的两个 reviewer 完成整体审查。本技能借鉴 Superpowers 的任务驱动方式，使用当前运行器的子 agent 工具，无外部插件、后台调度器或 Bash 脚本依赖。

## 1. 核对批准与恢复位置

确认用户授权实施，当前规格版本和计划版本与批准组合一致，关键问题已解决，路径、权限、依赖和当前代码状态已核实。仅要求规划时不启动；实质变化回到 [feature-plan](../feature-plan/SKILL.md) 修订确认。不因换会话重复索要仍有效的批准。

使用原计划作为唯一进度记录，按[计划模板](../../../docs/plans/TEMPLATE.md)保存当前项、执行者身份、基线、简报、交付与审查摘要、返工轮数、证据和下一步。启动或恢复时读取真实文件并核实在途 agent 状态、已有改动及证据；仍运行的任务先协调，不重复派工。原 agent 不可恢复时传递已验证交付和未完成范围给新 agent，保留原记录。

旧已批准计划缺独立规格书时，先按 feature-plan 的兼容规则整理关联规格；不借补文档增加未经批准的需求。

## 2. 为一个实现项准备简报

从依赖已满足的未完成项中，按计划顺序选择一项；多个实现项串行执行，上一项独立审查并由主 agent 验收通过后才启动下一项。不并行启动 implementer 与 infra 的实现工作。必要只读调查可以并行，但不能替代尚未满足的实现前置条件。

每个新实现项创建新的 implementer 或 infra 上下文；architect 在前期分析及重要设计偏差、事实调查时参与，不为凑齐角色反复调用。子 agent 不嵌套创建 agent；reviewer 由主 agent 派出，执行者自审不替代独立审查。

简报保存在原计划对应项中，使用 [交接模板](../../../agents/TASK_TEMPLATE.md) 提供以下材料：

- 当前清单项、批准文档组合、相关规格验收编号及原文约束、目标和非目标。
- 三域实际路径、工作目录、适用规则、必要接口与前置项已验收结果。
- 允许读写的具体范围、用户已有改动、验证方式与证据位置、必要依赖。
- 当前项开始前的基线、输出要求，以及本项简报在原计划中的定位。

不复制全段聊天或所有已完成任务的历史。需要长报告时才另存管理文档并引用，简报、报告和审查摘要默认直接放原计划；不为每轮交接新建文件。

主 agent 派工前记录相关仓库提交和已有未提交改动边界；未提交内容、未跟踪文件或无 Git 的区域，需要时在 test 保存相关文件的前置快照，供完整内容比对。不能只靠事后 git status 或 HEAD~1 推断本项差异，也不为方便审查擅自提交或初始化仓库。

每次创建前重读 [MODELS.md](../../../agents/MODELS.md)，显式传入角色模型和推理深度，按其规则记录实际参数及回复页脚。新上下文必须得到必要材料；工具不支持明确配置时报告限制，不静默降级或冒充已创建。

## 3. 接收实现与验证报告

执行者在分配范围内实现、进行针对性验证并自审，按角色共享格式返回：实际文件和结构变化、完整差异范围、工作目录与检查结果、证据、未完成项和阻塞。主 agent 保持调度职责，不在执行者工作期间改其文件，也不接管本项实现来绕过审查；必要调整先更新分派边界。

主 agent 核对实际交付。报告中有待完成工作、关键问题或缺失证据时，先补齐上下文、返工或记录受阻，不把“完成”标签当验收结果。结构变化由主 agent 按 [paths.md](../../../docs/paths.md) 更新，最迟在下一轮分派或审查前完成。

软件本体在 project/code，测试和所有辅助代码、差异导出、快照、原始日志及验证产物在 test，harness 只保存管理文档。只有用户明确要求或明确批准计划中的打包项时才生成最终安装包到 project/installpark；不额外提交、推送、合并或发布。

## 4. 派出两个并行 reviewer

每个实现项交付后，主 agent 创建与执行者及彼此都不同、上下文独立的两个 reviewer，并行审查。两者使用 MODELS.md 中同一 reviewer 角色配置，每次创建分别读取并显式传参，记录各自身份、维度、轮次和实际参数。提供相同简报、规格约束、受审版本、完整任务差异及基线、执行报告和验证证据；复验可恢复本项的两个实例。差异包含本项全部提交和未提交变化，不能只给最近一次提交；无 Git 时使用前置快照与当前文件比对。原始差异和快照保存 test，计划仅记录路径和覆盖范围。

两个实例独立读取实际文件，各自给出一个明确判断，不预先读取对方初次结论：

- **reviewer-spec／规格符合性**：本项对应行为、边界及验收是否满足，有无漏做或额外范围。
- **reviewer-quality／实现质量**：正确性、项目规范、相关回归风险、可维护性及测试和验证证据是否有效。

每份报告使用“建议通过／需返工／证据不足”，注明负责维度、轮次、实际覆盖版本和限制。两份齐全、均建议通过且覆盖同一最终版本，主 agent 核实后才验收；缺少任一报告、任一需返工或证据不足均不得通过。冲突按证据裁定，不能投票或用另一维度通过抵消；重复发现由主 agent 去重但保留两份来源与结论。跨维度的确凿缺陷也须报告。

两份报告返回前不改受审范围；出现外部变更则为两者更新受审版本并复核，不能混用版本。容量不足时两个独立实例顺序完成并注明实际未并行；缺少任一实例能力则记录验收阻塞，不降为一个 reviewer 兼任。检查应与本项风险相关；已有同版本证据有效时不机械重跑，有具体疑点或新差异影响结论时补充针对性验证。

发现缺陷或复验时，reviewer 调用 [bug-detect](../bug-detect/SKILL.md)，只返回去重后的记录提议，主 agent 串行写项目错误知识库。子 agent 不直接改共享记录。

## 5. 返工、逐项通过与中断恢复

主 agent 核实每项发现，记录接受修复或有证据拒绝的理由。需要修复时优先恢复原执行者，提供具体发现、验收与允许范围；原 agent 不可用或当前角色配置已改变时，重读配置创建新 agent，并交接已有成果与未解决事项。

修复后重跑受影响检查，主 agent 为本组两个 reviewer 提供相同最终版本与新增差异，各自复核原发现及相关回归；本维度未受影响时可复用有效证据，但仍需核对并确认当前版本。优先恢复原两个实例，不可恢复或角色配置改变时按新配置创建并交接。两份结论满足通过条件后，再由主 agent 核对证据。连续两轮同一问题且无新证据时，重查根因、方案及分派方式；必要时请 architect 分析，需用户决策则只提出具体问题。不能机械无限重试，也不能达到轮数后将未满足的需求、必需验证或阻塞缺陷“挂起后算完成”。

主 agent 仅在本项符合规格、质量及必要检查均满足后勾选通过，记录基线至最终差异范围、reviewer 结论和证据。记录完成与下一步后再派下一项；原始报告不另成为进度来源。

计划中纯审查条目直接由两个 reviewer 分工完成，主 agent 验收条目由主 agent 执行，不给 reviewer 的报告再递归安排审查。真正修改实现后仍须由两个实例复验并满足同版本通过条件。

缺少权限、依赖、运行器能力或必要决策时记录具体阻塞、已尝试动作、影响及恢复条件；不开始依赖该条件的实现。其他独立且已授权的只读调查、文档准备可以继续。恢复时重新核实受影响证据，保留仍有效的批准与已验收项。

## 6. 整体审查与最终验收

所有实现项通过后，主 agent 新建 reviewer-spec 和 reviewer-quality 两个上下文独立的实例，并行审查整份规格和功能开始基线后的完整最终差异。前者检查全功能验收覆盖与跨项行为，后者检查跨项接口、数据流、回归及最终证据有效性；共同遵守第 4 节两份独立、同版本报告的通过条件及容量规则。不能仅把逐项通过摘要当整体审查。

整体发现仍按修复、针对性验证、独立复验闭环处理；如更改了已验收项，重开受影响项并重新验收，不重做无关且证据仍有效的工作。全部必需检查、强制审查与主 agent 最终验收满足后，更新规格状态、路径索引和计划证据，将计划归档 completed 并修正规格中的计划链接。

最终回复说明完成内容、实际验证及限制。未完成、受阻、未运行的必需检查不能标为通过，验收完成不自动授权额外的 Git 操作或发布。
