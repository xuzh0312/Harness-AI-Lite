# Tech Stack Plan：技术栈与项目架构约束规划

主 agent 向用户进行多轮访谈和用户明确技术栈需求，同步整理进[项目简介](../../../README.md)与[技术栈与架构文档](../../../ARCHITECTURE.md)

## 适用范围与权限

当 feature-plan 技能发现技术栈不存在，用户选择'技术栈未确定共同讨论'后才允许调用此skill。

主 agent 从 Harness 显式读取本技能，不依赖全局安装或自动发现。

仅在这两份文档中更新已确认的项目细节和技术选择，保留三域与打包规则。

| 允许修改文件 | 文件位置 | 修改内容 |
|---|---|---|
| 项目简介 | ../../../README.md | 项目具体细节 |
| 技术栈与架构文档 | ../../../ARCHITECTURE.md | 技术栈 |

## 查明事实，用苏格拉底式访谈明确

主 agent 现在是苏格拉底，需要以苏格拉底的形式进行提问与追问。

### 具体流程

#### 1.明确需求：

| 方面 | 可以怎么问 | 回答会影响什么 |
|---|---|---|
| **1. 用户与核心流程** | “请选一位典型用户，从他打开软件开始，讲到他完成一次任务。”“第一版必须把哪条流程跑通？” | 确定主要交互方式，以及界面、计算、存储各自承担什么工作。 |
| **2. 运行环境与部署** | “软件具体在哪台设备上用，谁来安装？”“断网时，哪一步仍要能完成？”“能申请管理员权限吗？” | 判断网页、桌面端、移动端各自是否可行，是否需要本地运行或独立部署。 |
| **3. 数据与协作** | “数据从哪里来，最后要到哪里去？”“两个人会同时改同一条记录吗？”“换电脑后，哪些数据必须跟过去？” | 决定文件、本地数据库或服务端数据库是否合适，以及是否需要同步和冲突处理。 |
| **4. 规模与性能** | “拿一次最重的任务举例，一次要处理多少数据？”“用户能接受等多久？等待时还要继续做什么？” | 判断是否需要后台任务、流式处理、并行计算或硬件加速，也能得到可测量的验收条件。 |
| **5. 外部依赖与兼容** | “必须对接哪些设备、文件格式、接口或现有系统？”“有没有一个真实样例，或者已经能运行的 SDK 示例？” | 识别会直接限制操作系统、语言、运行时或库版本的依赖。 |
| **6. 安全、可靠性与恢复** | “哪些数据可以离开设备，谁有权查看或修改？”“如果保存时断电，最多能接受丢掉多少工作？恢复由谁操作？” | 明确权限、存储边界、事务、备份和恢复要求。 |
| **7. 交付与长期维护** | “第一版什么时候要交给谁使用？”“半年后谁来修问题、发更新？他熟悉什么技术？”“时间紧时，哪项可以推迟？” | 在可行方案中权衡学习成本、打包更新、运维负担和交付速度。 |

可以模仿下述案例进行追问：
- 先澄清词义。 “你说的‘本地’，主要是希望断网也能刷题，还是学校要求题库和答题记录始终留在这台电脑上？”这两项要求可以同时成立，但对数据存放位置的约束不同。
- 再用具体情境检验。 如果用户说“主要是断网能用”，就问：“假设考前一天完全断网，你需要完成哪些操作？”由此能区分只需离线答题，还是导入、搜索、错题统计也都要离线。
- 用反例找边界。 如果用户说“只有我自己用”，就问：“你在教室电脑做完一半，回宿舍后需要接着做吗？”单人使用仍可能涉及多设备数据迁移。
- 让用户排序。 如果用户还希望跨设备使用，就问：“第一版如果只能先做好一项，你更需要自动同步，还是能把记录导出、带走并恢复？为什么？”这个回答会直接影响第一版是否值得引入服务端。
- 把结论说回给用户核对。 “我目前理解的是，第一版要在 Windows 上断网完成导入、答题和错题回顾；换机时手动迁移可以接受。这个描述漏掉了哪种会让你没法使用的情况？”

通过明确这些问题将整个项目的具体细节整理写入[项目简介](../../../README.md)

#### 2.技术栈规划：

主 agent 通过之前的追问了解需求后明确整个项目的技术栈应该由哪些部分组成，并向用户逐一确认各部分采用什么技术，需要给用户你的建议。

用户确认完成后将技术栈写入[技术栈与架构文档](../../../ARCHITECTURE.md)中，作为后续功能规划和实现的基础且此技术栈不可擅自更改。

技术栈规划时需对关键选型写清「采用什么、由哪条约束决定、仍需验证什么」。比如，若最终确认单机离线使用、无并发写入、接受手动迁移，就把这些条件和 SQLite 的选择一起记录

### 追问方式

一次只问一个问题，按回答调整追问

优先使用运行环境提供的用户提问工具（如 AskUserQuestion）。每次只问一个具体问题，场景题开放作答，选型取舍可给出 2–4 个选项并允许自由回答。按工具实际支持的选项数和交互方式适配；无可用工具时，在对话中用同样格式逐题询问。等待用户回答再继续。

每次回答后简短回述新确定的内容。并检查回答是否暴露矛盾、顾虑、未验证假设、阻碍、回避或风险。发现影响需求的线索就优先沿它追问，后续问题只在前提明确时提出。不重复询问已回答内容。普通实施细节沿用项目惯例并在计划中说明，访谈聚焦会影响范围、用户行为、约束或验收的取舍。用户委托 agent 决定的细节可拟定默认方案，在文档中标明来源并交由用户审阅。

单一流程向用户进行整场访谈通常可有 10–15 题，简单明确后可只询问3-5题，仍有盲点时可到 20 题。用户明确要求结束时停止提问，保留未决事项。

### 结束条件

全部完成并补充完报告后告知用户并让用户检查[项目简介](../../../README.md)与[技术栈与架构文档](../../../ARCHITECTURE.md)是否符合预期。用户确认后，本技能完成并退出，否则继续按用户提出的不足继续访谈。
